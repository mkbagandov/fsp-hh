# ФСП — платформа найма ИТ-специалистов с подтверждённым грейдом

Решение спецтрека Федерации спортивного программирования на хакатоне «Лидеры цифровой трансформации — 2026».

**Обратная механика найма:** кандидат проходит опрос и адаптивный тест и попадает в категорию
«специализация × грейд»; работодатель описывает потребность, видит карту категорий и объяснимую
подборку и сам приглашает конкретного человека с обязательной зарплатной вилкой. Контакты
раскрываются только после согласия кандидата. Достижения из реестра ФСП усиливают профиль
внутри категории, а их отсутствие ничего не штрафует.

## Стек

- Backend: Go 1.26, chi, huma v2 (OpenAPI 3.1 из кода), pgx v5, sqlc, goose
- БД: PostgreSQL 18
- Frontend: React 19, TypeScript, Vite 6, Tailwind 4, TanStack Query; типы API генерируются из OpenAPI
- LLM: в MVP детерминированный эмулятор (`LLM_PROVIDER=mock`), адаптеры подключаются переменной окружения

## Быстрый старт (локально, без Docker)

1. Установить Go 1.26 (Go 1.21 и новее сам скачает нужную версию), PostgreSQL 16+, Node.js 22+ и `go-task`:
   `go install github.com/go-task/task/v3/cmd/task@latest`
2. Создать роль и базы:
   ```sql
   CREATE ROLE fsp_platform WITH LOGIN PASSWORD '...' CREATEDB;
   CREATE DATABASE fsp_platform OWNER fsp_platform;
   CREATE DATABASE fsp_platform_test OWNER fsp_platform;
   ```
3. `cp .env.example .env` и подставить пароль в `DATABASE_URL` / `TEST_DATABASE_URL`. Пример включает
   `APP_ENV=dev`: письма с кодами подтверждения видны на странице `/dev/outbox`, SMTP не нужен.
4. Собрать фронтенд: `task web:install`, затем `task web:build` — API раздаёт `web/dist` на `/`.
5. Заполнить демо-данными: `task seed` (необязательно, аккаунты — ниже).
6. `task run` (или `task dev` при установленном `air`) и открыть http://127.0.0.1:8080.
   Документация API — http://127.0.0.1:8080/api/v1/docs, проверка — `curl http://127.0.0.1:8080/api/v1/health`.
7. Вход через ФСП ID (необязательно): в соседнем терминале `task fspmock` — эмулятор ФСП ID и реестра
   достижений на :8090, участники `ivanov`, `petrova`, `sidorov` с паролем `fsp`.

Миграции применяются автоматически при старте (`MIGRATE_ON_START=true`). Для разработки фронтенда —
`task web:dev` (Vite на :5173 с прокси `/api` на :8080).

## Проверка за 10 минут

`task doctor` проверяет окружение — Go и Node, `.env`, подключение к базам, порт и сборку фронтенда — и
говорит, что исправить. Дальше по шагам:

| Шаг | Команда или действие | Ожидаемый результат |
|---|---|---|
| Окружение | `task doctor` | все строки с ✓ и «Всё готово» |
| API | `curl http://127.0.0.1:8080/healthz` | `ok` |
| Кабинет работодателя | http://127.0.0.1:8080/login, `demo-employer@seed.fsp.local` / `Demo1234!` | потребности, карта категорий, подборка с объяснениями |
| Подтверждение категории | у `demo-candidate@seed.fsp.local` — «PDF-профиль», QR-код внизу | страница `/verify/<id>` с категорией Backend × Middle без персональных данных |
| Тесты | `task test` | все пакеты `ok` (в том числе на пустой тестовой базе) |
| Сквозные сценарии | `task e2e:install` (один раз), `task e2e` | 14 passed |
| Валидация | `task validate` | `docs/validation/REPORT.md` совпадает с репозиторием, кроме даты прогона |

Типовые проблемы: нет `.env` — `cp .env.example .env`; `password authentication failed` — пароль роли в
`DATABASE_URL`; порт занят — `HTTP_ADDR` в `.env`; «фронтенд не собран» — `task web:install && task web:build`.

## Демо-данные

```bash
task seed            # сброс и генерация: 300 кандидатов с реальными тест-сессиями, 10 компаний, 15 потребностей, 20 вакансий, приглашения и отклики
task seed N=1000     # больше кандидатов
task seed:reset      # удалить всё, что создано сидом (аккаунты @seed.fsp.local и их компании)
```

Демо-аккаунты (пароль у всех `Demo1234!`):

| Аккаунт | Кто это |
|---|---|
| `demo-candidate@seed.fsp.local` | кандидат с подтверждённой категорией Backend × Middle и достижениями ФСП |
| `demo-candidate-new@seed.fsp.local` | новый кандидат без теста — для показа онбординга |
| `demo-employer@seed.fsp.local` | владелец компании «Платёжный сервис „Орбита“» с потребностями, подборками и вакансиями |
| `demo-admin@seed.fsp.local` | администратор: сводка, банк заданий и калибровка, аудит |

Синтетика детерминирована (`-seed 42`): скрытая θ кандидата задаёт вероятность верного ответа по 3PL, тест проходится через тот же сервис, что и у живых пользователей, поэтому статистика банка и категории — настоящие. Сценарий показа на 10 минут — в [docs/pitch/PITCH.md](docs/pitch/PITCH.md).

## Валидация

`task validate` — воспроизводимая процедура на синтетической популяции с известной истиной: точность θ̂ и грейда, test-retest (каппа Коэна), сравнение CAT с линейными тестами, устойчивость к угадыванию и утечке банка, информативность и дискриминативность семейств, калибровка сложности, качество подбора (NDCG@10). Результат — `docs/validation/REPORT.md` с SVG-графиками; при том же seed отчёт совпадает побайтно, кроме строки с датой и временем прогона. `task validate:load` добавляет нагрузочный раздел по запущенному стенду.

## E2E-тесты

```bash
task e2e:install   # один раз: Chromium для Playwright
task e2e           # сборка фронтенда, пересоздание базы fsp_platform_e2e с сидом, API на :18080, 14 сценариев
task e2e:demo      # те же главные сценарии с видео и замедлением
```

Сценарии: регистрация кандидата с кодом из письма → онбординг → адаптивный тест → результат с разбором; работодатель → компания → потребность текстом → карта категорий → объяснимая подборка → приглашение с вилкой → кандидат принимает → контакты раскрыты; вакансия → отклик → отказ с причиной; матрица доступа (контакты без согласия закрыты, чужое не видно, роли разделены, скрытый кандидат виден только компании, на вакансию которой откликнулся); загрузка PDF-резюме (PDF-профиль одного кандидата разбирается для другого в изолированном процессе) → черновик → применение; админка и `/metrics`. Стенд изолирован: база `*_e2e` пересоздаётся перед каждым прогоном (`cmd/seed -recreate-db` отказывается работать с другими базами).

## Безопасность

Модель угроз, механизмы защиты и приватности, результаты ревью безопасности с регрессионными тестами и чеклист запуска в prod — [docs/06-security.md](docs/06-security.md). Коротко: контакты раскрываются только по гранту; скрытые кандидатом поля не участвуют в подборе и объяснениях; без `APP_ENV` процесс стартует как prod и требует HTTPS-cookie и SMTP; PDF от пользователя разбирается в изолированном процессе с тайм-аутом.

## Тесты

`task test` — модульные и интеграционные тесты Go (база `fsp_platform_test` из `TEST_DATABASE_URL`), включая сквозной сценарий через настоящий HTTP-обработчик (`internal/server`); `task e2e` — браузерные сценарии Playwright; `task validate` — валидация механик; `task check` — форматирование, vet, линтер и тесты перед коммитом.

## Презентация и демо-ролики

Готовые материалы — в `docs/pitch/`: презентация `fsp-pitch.pdf` и `fsp-pitch.pptx`,
текст выступления с таймингом и вероятными вопросами — [PITCH.md](docs/pitch/PITCH.md), демо-ролики с

## Структура

```
cmd/api                 точка входа HTTP API; с аргументом pdftext-worker — изолированный разбор PDF
cmd/seed, cmd/validate  демо-данные и валидация механик
cmd/fspmock             эмулятор ФСП ID (OIDC, пути Keycloak) и реестра достижений
internal/config         конфигурация из окружения (без APP_ENV — prod)
internal/server         сборка приложения: сервисы, мейлер, разбор PDF, HTTP-обработчик
internal/domain         доменные типы и правила
internal/app            сценарии использования (use cases) по модулям
internal/transport/http chi + huma, операции API
internal/storage/postgres подключение, миграции, sqlc
internal/infrastructure почта, LLM-адаптеры, PDF, OIDC, реестр ФСП
internal/validation     процедура валидации механик и генератор отчёта
pkg/irt, pkg/itembank   движок IRT/CAT и банк параметрических заданий
web                     SPA: кабинеты кандидата, работодателя и администратора; E2E на Playwright
assets/brand            фирменные шрифты, логотипы, паттерн ФСП
docs                    архитектура, механики, ADR, валидация, API, презентация (docs/pitch)
```
