# 01. Доменная модель: термины, роли, инварианты

Документ фиксирует язык предметной области платформы «ФСП» и правила, которые код обязан
соблюдать. Проверочный список для ревью — в конце. Статусы и переходы — `02-data-model.md`,
подбор — `03-matching.md`, тестирование — `04-testing.md`, ФСП — `05-fsp-integration.md`.

## 1. Назначение платформы в одном абзаце

Кандидат регистрируется, заполняет профиль (вручную или из PDF), проходит опрос и адаптивный тест
и получает **категорию** — пару «специализация × грейд», подтверждённую тестом, а не самоописанием.
Работодатель описывает **потребность**, видит **карту категорий** с рыночной обратной связью
и **подборку** кандидатов с объяснением каждого места, затем направляет **приглашение** с
обязательной зарплатной вилкой конкретному человеку. Контакты раскрываются только после того,
как кандидат принял приглашение или сам откликнулся на вакансию. Достижения из реестра ФСП
усиливают профиль внутри категории; их отсутствие ничего не штрафует.

## 2. Глоссарий

| Термин (RU) | Код | Определение |
|---|---|---|
| Пользователь | `user` | учётная запись с e-mail, паролем или входом через ФСП ID и ролью |
| Кандидат | `candidate` | пользователь с ролью `candidate`; владеет профилем, категориями, приглашениями, откликами |
| Работодатель | `employer` | пользователь с ролью `employer`, прикреплённый к компании |
| Компания | `company` | организация-работодатель: профиль, потребности, вакансии, приглашения, репутация |
| Администратор | `admin` | роль оператора платформы: банк заданий, аудит, модерация (концепция) |
| Специализация | `specialization` | направление деятельности: `backend`, `frontend`, `data_ml`, `devops`, `qa`, `security` |
| Грейд | `grade` | уровень навыков `junior` / `middle` / `senior`, подтверждаемый тестом |
| Категория | `category` | пара специализация × грейд с статусом подтверждения; то, что видит работодатель |
| Опрос | `survey` | анкета при регистрации: отрасль, специализация, стек, заявленный грейд, стаж |
| Тест-сессия | `test_session` | одно прохождение адаптивного теста на заявленный грейд |
| Семейство заданий | `item_family` | параметрический генератор заданий с темой, грейдом и IRT-параметрами |
| Экземпляр задания | `item_instance` | конкретный вариант, построенный семейством по seed |
| Оценка способности | `theta` (θ) | положение кандидата на единой шкале IRT; `se` — стандартная ошибка оценки |
| Решение по грейду | `grade_decision` | `confirmed`, `not_confirmed`, `upgrade_suggested` |
| Навык | `skill` | элемент справочника навыков с синонимами; у кандидата — с источником и уровнем |
| Источник навыка | `skill_source` | `declared` (указан вручную), `resume` (из PDF), `test_confirmed` (подтверждён темой теста) |
| Потребность | `need` | описание того, кто нужен компании; основа подборки |
| Карта категорий | `category_map` | агрегаты по категориям под потребность: численность, подтверждённость, ФСП, покрытие вилкой |
| Подборка | `selection` | ранжированный список кандидатов под потребность |
| Версия подборки | `selection_version` | снимок подборки с параметрами фильтра; уточнение создаёт новую версию |
| Объяснение | `explanation` | структурированные факты «за» и «против» по каждому кандидату в подборке |
| Приглашение | `invitation` | предложение компании конкретному кандидату: текст, вилка, способ связи, статус |
| Вакансия | `vacancy` | опубликованная позиция с вилкой; дополнительный сценарий |
| Отклик | `application` | инициатива кандидата по вакансии; открывает контакты компании-владельцу |
| Грант на контакты | `contact_grant` | факт раскрытия контактов кандидата компании (по принятию или отклику) |
| Микро-задание | `micro_task` | короткая задача компании, адресно предложенная кандидату категории |
| Достижение ФСП | `fsp_achievement` | запись реестра ФСП о результате участника |
| ФСП ID | `fsp_id` | идентификатор участника в системе ФСП (OIDC, в будущем Keycloak) |
| Согласие | `consent` | зафиксированное согласие на обработку / публикацию / получение данных ФСП |
| Видимость | `visibility` | режим кандидата: `open` (открыт к предложениям), `passive`, `hidden` |
| Свежесть | `freshness` | давность последнего теста и активности по микро-заданиям |
| Cooldown | `grade_cooldown` | минимальный интервал между попытками сменить грейд (по умолчанию 90 дней) |

Правило именования: в коде, БД и API — английские коды из таблицы; в интерфейсе и документах —
русские термины. Синонимы не вводятся («соискатель» в тексте допустим, в коде только `candidate`).

## 3. Роли и права

| Действие | candidate | employer | admin |
|---|---|---|---|
| Свой профиль, контакты, приватность, согласия | полный | — | чтение в аудите |
| Опрос, тест, категория, история грейдов | свой | — | статистика без ПДн |
| Карта категорий, подборка, поиск по банку | — | своя компания | — |
| Карточка кандидата без контактов | — | да (с учётом приватности и видимости) | — |
| Контакты кандидата | свои | только при активном гранте | — |
| Приглашения | входящие: просмотр, принять, отклонить | исходящие: создать, отозвать, статусы | — |
| Вакансии | список, отклик, свои отклики | свои: создать, опубликовать, закрыть, отклики | модерация (концепция) |
| Микро-задания | предложенные: принять, решить | свои: создать, оценить | — |
| Банк заданий, калибровка | — | — | да |
| Аудит-лог | — | — | да |

Проверка прав выполняется в слое use case; HTTP-слой только извлекает идентичность.
Любой доступ к контактам и любое изменение приватности пишется в `audit_log`.

## 4. Инварианты (нарушать нельзя)

1. **Категория определяется тестом.** Поля `candidate_categories.grade_code` и `status`
   меняются только сервисом тестирования по результату сессии. Ни кандидат, ни работодатель,
   ни разбор резюме их не меняют.
2. **Грейд не понижается принудительно.** Неудачный тест даёт статус `not_confirmed`, но не
   удаляет ранее подтверждённую категорию более низкого грейда.
3. **Cooldown.** Повторный тест на тот же или более высокий грейд возможен не раньше
   `next_test_allowed_at`; тест на грейд ниже — сразу.
4. **Вилка обязательна.** `salary_from` и `salary_to` заданы, `0 < from ≤ to`, в рублях, целые —
   для вакансии при публикации и для приглашения при создании.
5. **Контакты закрыты.** Контакты кандидата попадают в ответ API компании только при наличии
   активной записи `contact_grants` (создаётся при `invitation.accepted` или `application.sent`).
6. **Кандидат видит только своё.** Любой запрос кандидата фильтруется по его `user_id`.
7. **Статусы меняются только по разрешённым переходам** (см. `02-data-model.md`), с записью
   времени перехода и актора.
8. **Подборка не теряется.** Уточнение фильтров создаёт новую `selection_version`;
   предыдущие версии остаются доступны.
9. **Нет истории ФСП — нет штрафа.** Компонент `s_fsp` равен 0, остальные компоненты
   считаются как обычно; в интерфейсе — нейтральное состояние.
10. **Согласие предшествует публикации.** Профиль попадает в подборки только при действующем
    согласии `publication`; отзыв согласия скрывает профиль и отзывает активные гранты не нужно —
    уже раскрытые контакты остаются у компании (так работает и офлайн), но новые не выдаются.
11. **Семейства заданий детерминированы по seed; ответ вычисляется, а не хранится в тексте.**
12. **LLM не принимает решений.** Любой вывод LLM-адаптера (в MVP — эмулятора) — только
    черновик для подтверждения пользователем или вспомогательный текст.

## 5. Справочники (источник — `internal/domain/refdata`)

- Специализации: `backend` Backend-разработка, `frontend` Frontend-разработка, `data_ml` Data Science / ML,
  `devops` DevOps / SRE, `qa` QA / автоматизация тестирования, `security` Информационная безопасность.
  Служебная `common` — общий блок заданий, не выбирается кандидатом.
- Грейды: `junior`, `middle`, `senior` (порядок строгий; `Lead` — roadmap).
- Темы заданий по специализациям — `04-testing.md`, раздел 3.
- Форматы работы: `office`, `hybrid`, `remote`.
- Дисциплины ФСП: `algorithmic`, `product`, `security`, `robotics`, `uav`; уровни `regional`,
  `national`, `international`; виды результата `place`, `rank`, `rating`.
- Причины отказа от приглашения: `salary_below`, `not_looking`, `role_mismatch`, `format_mismatch`,
  `company`, `other`.
- Навыки: `skills.yaml` (~300 записей с синонимами и группами), загружается в таблицу `skills`
  при миграции/сидировании; синонимы используются разбором резюме и потребности.

## 6. Чеклист ревью доменной логики

- Контакты в ответе API — есть ли проверка гранта?
- Вилка валидируется в домене, а не только во фронтенде?
- Переход статуса — через метод домена с проверкой допустимости?
- Изменение категории — только из сервиса тестирования?
- Новая версия подборки создана, старая не перезаписана?
- Кандидат без ФСП получает те же компоненты, что и остальные, минус буст?
- Аудит записан для раскрытия контактов и изменения приватности?
