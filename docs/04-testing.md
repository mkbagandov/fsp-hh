# 04. Механика тестирования и категоризации

Критерий (25 %): устойчивость к распространению заданий, согласованность результата при
повторном прохождении, дискриминативность, соответствие экспертной оценке, корректность
категоризации, качество процедуры валидации. Документ описывает механику; результаты
проверки — в `docs/validation/REPORT.md` (этап 15).

## 1. Путь кандидата

1. **Опрос**: отрасль → специализация → основной стек → заявленный грейд → стаж. Тест доступен по
   специализациям с собственным банком заданий (не меньше 10 семейств без общего блока): сейчас это
   Backend, Frontend, Data/ML и DevOps; QA и ИБ есть в справочнике и профиле, их банки в разработке.
   Стаж сохраняется как атрибут, на грейд не влияет (ответ организаторов VS.1).
2. **Тест на заявленный грейд**: адаптивный, 12–20 заданий, уникальные варианты, таймер на задание.
3. **Решение**: `confirmed` / `not_confirmed` / `upgrade_suggested`, θ и доверительный интервал,
   процентиль в категории, пояснения к заданиям.
4. **Категория**: `specialization × grade` со статусом; видна работодателям.
5. **Повторы**: тест ниже уровнем — сразу после `not_confirmed`; тот же или выше — после cooldown
   (90 дней) или по предложению `upgrade_suggested`.

## 2. Почему не «единый набор» и не «нейрогенерация под каждого»

Единый набор заданий утекает за дни: ответы расходятся между участниками рынка, и тест
превращается в проверку доступа к ответам. Генерация уникальных заданий нейросетью решает
утечку, но ломает сопоставимость: сложность двух сгенерированных задач неизвестна, значит,
грейды разных кандидатов несравнимы, а результат при повторном прохождении нестабилен.

Наш подход — **параметрические семейства заданий + теория ответов на задания (IRT)**:
семейство — программа-генератор с известными (априорно и по калибровке) параметрами
сложности и дискриминативности; экземпляр уникален для кандидата, но измеряется на той же
шкале, что и экземпляры других кандидатов. Это даёт одновременно устойчивость к утечке
(утёкший ответ не подходит к другому варианту) и сопоставимость (единая шкала θ).

## 3. Банк заданий

- Семейство (`pkg/itembank.Family`): специализация, тема, целевой грейд, формат, параметры
  IRT `a, b, c`, лимит времени; `Generate(seed)` строит экземпляр и вычисляет ответ.
- Форматы: один из N, несколько из N, число, короткий текст, «что выведет код», порядок, результат SQL.
- Инварианты каждого семейства проверяет `itembanktest.CheckFamily`: генерация детерминирована по seed,
  из 200 seed получается не меньше 150 различимых экземпляров, канонический ответ принимается,
  заведомо неверный отклоняется, в тексте нет заглушек.
- Темы по специализациям:

  «что выведет код» 11, несколько из N 9, порядок 8, результат SQL 7, короткий текст 6. Рост банка до

## 4. Модель измерения (IRT, 3PL)

Вероятность верного ответа кандидата со способностью θ на задание с параметрами `(a, b, c)`:

`P(θ) = c + (1 − c) / (1 + exp(−a (θ − b)))`

- `a` — дискриминативность (крутизна), `b` — сложность (точка, где P = (1 + c)/2), `c` — угадывание.
- Оценка θ — **EAP** (апостериорное среднее) на сетке θ ∈ [−4, 4] с шагом 0.05 и нормальным
  априором N(μ₀, 1), где μ₀ зависит от заявленного грейда (junior −0.8, middle 0.1, senior 0.9);
  `SE` — апостериорное стандартное отклонение.
- Информация Фишера задания: `I(θ) = a² (P − c)² (1 − P) / ((1 − c)² P)`.

## 5. Адаптивный алгоритм (CAT)

```
θ̂ ← μ₀(заявленный грейд); SE ← 1.0; asked ← ∅; topics_asked ← {}
повторять:
    кандидаты ← семейства специализации ∪ common, не в asked, enabled,
                 exposure_rate < 0.20, тема не превышает квоту
    отсортировать по I(θ̂) убыванию; взять top-5; выбрать случайно (seed сессии)  — randomesque
    экземпляр ← family.Generate(seed_session ⊕ position)
    показать; получить ответ; is_correct ← Check(instance, submission)
    θ̂, SE ← EAP(ответы)
    остановка: (SE ≤ 0.30 и задано ≥ 12) или задано = 20 или время сессии истекло
```

- **Баланс тем**: первые 8 заданий покрывают не менее 5 разных тем; ни одна тема не превышает
  30 % заданий сессии.
- **Контроль экспозиции**: доля сессий за 30 дней, где семейство было показано, ≤ 20 %; при
  превышении семейство временно исключается из выбора. Плюс randomesque (случайный выбор из
  top-5 информативных) — у двух кандидатов с одинаковой θ разные траектории.
- **Стартовая точка от заявленного грейда** ускоряет сходимость и делает тест «на заявленный
  грейд», как требует ТЗ; при этом оценка остаётся несмещённой: априор слабый (σ = 1).

## 6. Решение по грейду

Полосы на шкале θ (стартовые, калибруются на синтетике и пересматриваются по данным):
junior `θ < −0.5`, middle `−0.5 ≤ θ < 0.7`, senior `θ ≥ 0.7`.

- Заявлен грейд G с нижней границей `L_G`. Подтверждён, если `P(θ ≥ L_G | ответы) ≥ 0.70`
  (вероятность по апостериорному распределению, а не точечная оценка).
- У Junior полоса снизу не ограничена, поэтому для подтверждения задан минимальный уровень
  `θ ≥ −1.5` (решает около трети заданий уровня Junior). Без него «Junior подтверждён» получал бы
  и угадывающий: в валидации до введения порога — 100 % угадывающих, после — 0 %.
- `upgrade_suggested`, если `P(θ ≥ L_{G+1}) ≥ 0.80` и грейд выше существует.
- Иначе `not_confirmed`: кандидату сразу доступен тест на грейд ниже; в профиле — статус
  «грейд не подтверждён», ранее подтверждённые категории сохраняются.
- Процентиль — доля кандидатов категории с θ ниже; пересчитывается при обновлении `category_stats`.

Почему вероятности, а не порог по точке: при SE 0.3 разница 0.1 по θ ничего не значит;
вероятностный критерий делает решение согласованным при повторном прохождении (test-retest).

## 7. Калибровка параметров

1. Априорные `a, b, c` задаёт автор семейства по правилам скилла.
2. После накопления ≥ 30 ответов на семейство сложность обновляется байесовски:
   `b ← (κ·b_prior + n·b_emp) / (κ + n)`, где `b_emp` — решение уравнения `mean P(θᵢ; a, b, c) = p̂`
   по итоговым θ̂ ответивших, `κ = 20`. Пересчёт (`testing.Service.Recalibrate`) идёт всегда от
   априорной сложности, выполняется при старте API, раз в сутки и по кнопке в админке
   (`POST /admin/items/recalibrate`); адаптивный тест сразу использует новые значения.
   Калиброванная сложность переживает перезапуск, пока автор не изменил априорную в коде.
3. Дискриминативность автоматически не пересчитывается: админка показывает по каждому семейству
   разделение θ ответивших верно и неверно, экспозицию и предупреждения; слабые семейства
   выключаются без деплоя. Функция `irt.CalibrateDiscrimination` готова, но включится после
   проверки на синтетике.
4. На синтетике (этап 15) проверено восстановление известной сложности: ошибка `b` снижается
   с 0,22–0,25 до 0,09–0,14 (отчёт валидации, раздел 7).

## 8. Устойчивость к распространению заданий

| Угроза | Мера |
|---|---|
| Утечка текста заданий и ответов | ответ зависит от варианта: семейство генерирует данные и вычисляет ответ; утёкший «ответ» не подходит к другому seed |
| Утечка самих генераторов (код открыт) | чтобы ответить, нужно выполнить вычисление для своего варианта — это и есть навык; формулировки и дистракторы варьируются |
| Коллективный «банк ответов» | адаптивные траектории и randomesque — наборы заданий разные; экспозиция семейства ≤ 20 % |
| Угадывание | параметр `c`, форматы без вариантов (число, текст, код) для части заданий |
| Повторное «прощупывание» теста | cooldown 90 дней на тот же/высший грейд; перемешивание вариантов; таймер |
| Подмена/помощь во время теста (вне MVP, большой плюс по ответу FTT.4) | телеметрия: потери фокуса, вставка из буфера, аномально быстрые верные ответы → флаг «требует проверки» без автоматических санкций; roadmap — прокторинг |

Эксперимент в валидации: «атакующий» знает правильные ответы N случайных экземпляров
из k семейств; измеряем прирост θ̂ по сравнению с его истинной θ — ожидаем статистически
незначимый прирост при любой доле утечки, так как ответы не переносятся между seed.

## 9. Регулярные микро-задания (концепция, не реализовано)

Адресные короткие задачи от работодателей поддерживают профиль актуальным: предложение не
чаще раза в неделю, решение/подход оценивает работодатель, оценка влияет на свежесть и даёт
бейдж. Они не меняют грейд (грейд — только тест), но дают работодателю свежий сигнал. В модели
данных заложен вид уведомления `micro_task_offered`; сценарий — в плане развития.

## 10. Что показываем жюри

- Экран теста и результат с доверительным интервалом и объяснением решения.
- Демонстрация двух кандидатов с одной θ и разными наборами заданий.
- Отчёт валидации: test-retest (каппа Коэна, корреляция θ̂), точность грейда против истины
  (точная и ±1), дискриминативность по семействам, эксперимент с утечкой.
